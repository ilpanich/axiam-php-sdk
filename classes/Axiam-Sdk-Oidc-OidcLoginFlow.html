OidcLoginFlow.php : 56

Shared "Login with AXIAM" core (CONTRACT.md §12) — the ONE begin/complete + state-store + error-mapping path BOTH {@see \Axiam\Sdk\Laravel\OidcLoginController}/ {@see \Axiam\Sdk\Laravel\OidcCallbackController} and {@see \Axiam\Sdk\Symfony\OidcLoginController}/{@see \Axiam\Sdk\Symfony\OidcCallbackController} call, mirroring the TypeScript reference's `middleware/oidcLoginCore.ts` (the ONE §12 path, exactly as `AccessEnforcer` is the one §11 path shared by both framework bridges in this SDK).

Framework-agnostic on purpose: it takes plain values in and returns a discriminated OidcLoginOutcome out, so each framework controller only has to translate an outcome into that framework's redirect/JSON response. It writes no session of its own and touches no framework request/response object: the one cookie it needs — the browser-binding cookie of CONTRACT.md §12.8 (contract 1.68; C7) — is handed to the controller as a finished Set-Cookie value (OidcLoginOutcome::$setCookie) and read back from the request by the controller, which passes its value to self::complete().

Browser binding (§12.8 rule 1; C7). begin() draws a fresh random value, stores its SHA-256 on the state entry and hands the value back as the __Host-axiam_oidc_bind cookie; complete() consumes the entry FIRST and then refuses, with the same 401 an unknown state gets, any callback that does not present the cookie whose digest the entry holds — before any token request and before $onSuccess. Without it, knowing a live state was treated as proof that the callback came from the browser that started the login, so an attacker could finish THEIR login in a victim's browser. There is no way to switch the binding off.

return_to (§12.8 rule 3; C6). Only a same-origin relative path is ever stored or followed (self::isSafeReturnTo()).

The state store is what makes the two HTTP requests of a redirect flow into one login: oidcBegin produces state/nonce/code_verifier on the login request, and only state survives the round trip through the IdP, so the other two must be parked somewhere the callback request can reach (§12.3 rule 1 — the SDK itself stores nothing on its own).

BOTH framework integrations are optional and off by default (CONTRACT.md §12, plan T8 item 2): this class, and the controllers built on it, are only ever required when an application explicitly wires them into its own routing — nothing in AxiamServiceProvider or AxiamBundle registers a route automatically.

complete()

OidcLoginFlow.php : 288

Step 2 — validate the callback, consume the stored state, check it is the browser that started the login, exchange the code, and hand back the post-login response (CONTRACT.md §12.1 `oidc_exchange`, §12.8).

public complete(string|null $state, string|null $code[, string|null $error = null ][, string|null $errorDescription = null ][, string|null $successRedirect = null ][, callable(OidcTokenSet, OidcStateEntry, mixed): void|null $onSuccess = null ][, string|null $bindingCookie = null ][, mixed $request = null ]) : OidcLoginOutcome

Order (§12.8 rule 1 (c)): the IdP error, then missing state/code, then consume the entry, then the binding check, then the exchange, then $onSuccess. Consuming comes first so the state is single-use whatever happens next.

Failure mapping (port-brief addendum item 19):

  • IdP returned $error instead of a code → 401 authentication_failed;
  • $state or $code missing → 400 invalid_request;
  • $state unknown, already consumed, or expired → 401 authentication_failed;
  • $bindingCookie missing, the entry carries no bindingDigest, or the digest of the cookie differs (compared in constant time) → the SAME 401 authentication_failed, with the SAME message, so the refusal does not say which check failed. The code is NOT exchanged (no request reaches the token endpoint) and $onSuccess is NOT called;
  • any §12.4 ID-token failure or OAuthProtocolError (an AuthError sub-type) → 401 authentication_failed;
  • NetworkError → 503 oidc_unavailable, never a silent success;
  • any other AxiamException of the exchange (an AuthzError, say) → 401;
  • ANY other exception — the application's $onSuccess throwing, the state store failing, a defect → 500 login_failed (the exception is not rethrown; its class, never its message, is logged). The cookie clear is the guarantee here: an exception that left complete() would reach the framework's error page with no clearing Set-Cookie (§12.8 rule 1 (d)). An application that wants its own handler to see a failure of $onSuccess catches it inside the closure and records it there.

EVERY outcome carries a clearing Set-Cookie for the binding cookie (OidcLoginOutcome::$setCookie); the controller MUST send it (§12.8 rule 1 (d)).

$onSuccess, when given, runs with the validated OidcTokenSet, the consumed OidcStateEntry and — third — $request, the framework request that completed the sign-in, exactly as the controller handed it over (§12.8 rule 2). It is where an application establishes its OWN session (sign a cookie, write a session row, …) on THAT request, with no ambient request context needed. This SDK deliberately does NOT do this for you: what a session means is the application's decision. A two-parameter closure keeps working: PHP ignores the extra argument.

The post-login destination is $successRedirect when given, else the stored return_to — but only if it is still a same-origin relative path (self::isSafeReturnTo()); one that is not (an entry from a caller-supplied store, or older glue) is not followed, and the JSON summary is returned instead (§12.8 rule 3).
