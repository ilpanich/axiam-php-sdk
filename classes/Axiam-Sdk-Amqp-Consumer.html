Consumer.php : 59

php-amqplib blocking consume loop with HMAC verify-before-handler (CONTRACT.md §8, D-04).

This is NOT a web-request path — consume() blocks on $channel->wait() for the lifetime of the process. It is meant to run on a long-running runtime (a dedicated CLI worker process), restarted by a process supervisor on exit (see bin/axiam-amqp-worker.php — no in-SDK auto-reconnect loop, Pitfall 6).

A consumer is TYPED (contract 1.69, §8 step 2c, D-9): it is configured with the ONE signed type it consumes (SignedEventType) and the tenant whose subkey $signingKey is, and checks the canonical bytes against that type's layout only — before the HMAC and before any decode. A validly signed body of another type (every tenant-signed shape shares the key) is refused as malformed and never reaches the application; run two consumers to consume both.

Every discard (§8 rule 4, "Every SDK consumer, field by field", D-8) logs exactly one warning whose context is timestamp, exchange, routing_key, tenant_id (the consumer's OWN configured tenant, never one read from the body) and reason, the first that applies in the contract's order: malformed, unsigned, signature, key_version, stale, replay. It never carries a signature, a nonce, a key or any part of the body. No body escapes the consumer (D-10): empty, BOM-prefixed, not UTF-8, deeply nested or truncated bodies are discarded as malformed and the loop goes on to the next delivery.

Ack/nack semantics (verifyAndDispatch):

  • any discard (malformed, unsigned, signature, key_version, stale, replay) -> nack WITHOUT requeue (fail closed, poison-loop risk)
  • Handler throws AmqpDropMessage -> nack WITHOUT requeue (application-declared poison message)
  • Handler throws any other \Throwable -> nack WITH requeue (transient failure, retry)
  • Handler completes successfully -> ack

The HMAC is verified over the RECEIVED BYTES (the body with its trailing hmac_signature member cut out), never over a re-serialization, and the handler is given the value parsed from those same verified bytes (axiam#882, C2) — see Hmac. A body with a duplicate key, content after the object, or a signature that is not the trailing member is nacked without requeue and the handler never runs.

NEW-4 (CONTRACT.md §8 "v2 — Replay Protection", hard cutover): once the HMAC verifies, the delivery is ADDITIONALLY rejected (same nack-without- requeue path) when key_version < 2, issued_at falls outside the ±skew freshness window, or nonce has already been seen. nonce and issued_at are inside the verified bytes, so they are covered by the HMAC with no canonicalization step — only the ReplayGuard gates are new. See ReplayGuard for the full policy.
