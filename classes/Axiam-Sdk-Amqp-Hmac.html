Hmac.php : 36

HMAC-SHA256 verify-before-handler primitive for inbound AMQP messages (CONTRACT.md §8).

Verify the received bytes, and hand the handler the same bytes (axiam#882, C2). The server writes a signed message as a compact JSON object whose LAST member is "hmac_signature":"<hex>", signed over the bytes before it (the object closed with }). This class cuts that trailing member out of the body exactly as it was delivered and computes the HMAC over what is left. It never rebuilds the signed bytes by decoding and re-encoding the body: encoders disagree on string escaping (PHP's json_encode writes é for é unless told otherwise and \/ for /; Go's escapes <, > and &; serde_json writes all of them raw), so a re-serialization fails to verify a genuine message whenever a field contains a character the two encoders spell differently, and — worse — a body can verify as one thing while a reader of the original bytes sees another.

What is refused, all as false / null, never an exception (§8.3 strict mode):

  • a body that is not a JSON object, or that repeats a key at any depth (a duplicate is read one way by json_decode, which keeps the last, and another way by a parser that keeps the first), or that has any content after the closing brace;
  • a body that does not END in exactly ,"hmac_signature":" + 64 hex digits + "} (a message the server did not write, or one re-encoded on the way, or one with whitespace added), or whose top-level hmac_signature is not that trailing member;
  • a signature that does not match, compared in constant time.

self::verifiedCanonical() returns the bytes the HMAC covered; the caller builds its view of the message from THOSE bytes (json_decode() of them), which is what Consumer::verifyAndDispatch() does.
